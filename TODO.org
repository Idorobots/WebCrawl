* Scenery Refactor
All object visuals should be done with animations. Some animations can have a single frame, but they should adhere to the comon animation interface.

- Each in-game scenery object should have a spec that includes various animations (idle, destroyed, other optional animations), effect animations (damage, destroy) as well as other properties (hitpoints, position, footprint, hitbox, loot, etc).

- Each scenery object should have a `destructible` property that determines if the object can take damage and become destroyed.

- Each scenery object should have a `blocking` property that determines if it's passable and if it blocks bullets. When true, the player and monsters can't move through this scenery object. If the scenery object is destructible, it should become passable when destroyed.

- The `idle` animation should be the default animation displayed (for now, let's use the primary scenery sprite as the entire animation - 1 frame only).

- Some object can have additional animations that can be triggered externally. These should be displayed whenever its needed (for instance, the enemy spawner should periodically display the animation of spawning an enemy).

- When the object is destructible and takes damage, it should display the `damage` effect animation. When the object is destroyed, it should display the `destroy` effect animation.

- When the object becomes destroyed, the `destroyed` animation becomes the displayed animation (for now, let's use a debris sprite as the entire animation - 1 frame only, when a scenery object can have different debris sprites, it should be selected at generation time deterministically, based on the room hash).

- When a scenery object is destroyed, it no longer can be interacted with and it should display no health bar.

- In addition to that, scenery should have a pre-generated loot attached to it. Upon destruction, the scenery object remains in-game, but becomes destroyed and spawns its loot at its location.

It's OK if the specs are not entirely static - it's perfectly fine to have a function generating a scenery object based on the room seed.

The goal is to be able to generate a room with all its scenery objects that already include the loot, specific animations etc. The arch goal is to be able to generate the entire graph of rooms and objects within them, deterministically, and then treat that as state that evolves during the game and is renderable via phaser.

* Level generator/renderer refactor
The level regenation sholud be carried out entirely on the client side. The server component should just serve the assets and download the desired URL returning the HTML contents.

The client-side generator should first traverse the returned DOM and bulid a graph of rooms and corridors, which is then laid out to form the level map. Then for each of generated room and corridor, the level generator should deterministically generate themed scenery and enemies and their loot. That generated level should be a large data structure that serves the purpose of the game state.

The client-side level renderer should take the large data structure and render the level using datastructure-stored layout, scenery, enemies and loot. It is OK to limit the rendered level to just the "visible" rooms - the rooms that the player's viewport is currently showing.
The player character should be rendered onto the level and the viewport camera should be focused on the player.

* Room layout
We currently have different hard-coded shapes of rooms, but it would be nice to be able to build arbitrary shapes out of tiles of floors and walls. The layout engine should first plan the level map and generate room shapes, then connect them with corridors. Each corridor should start and end with a door, either horizontal or vertical. Rooms & corridors should be constructed in such a fashion, that they can all be enclosed with tiled wall pieces.

* Hidden rooms
`display: none` rooms are considered "hidden rooms". The renderer should not show corridors leading to those hidden rooms from the other rooms. Only when the player "discovers" the room (enters one of the corridors leading into the hidden room), should it appear together with its corridors on the viewport and on the minimap.
There should be no doors generated leading to these hidden rooms, only walls with a passable section (essentially a "holographic" wall), to maintain the illusion of those rooms being hidden.
